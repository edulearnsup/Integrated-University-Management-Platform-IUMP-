## ۱. معرفی و هدف

این سند نیازمندی‌های عملکردی، غیرعملکردی، معماری، مدل داده، رابط کاربری،
امنیت و APIهای ماژول «نقشه مهارت‌ها و علایق دانشجو» را مشخص می‌کند.

این ماژول به هر دانشجو امکان می‌دهد نقشه‌ای بصری و تعاملی از مهارت‌ها،
علایق، حوزه‌های مورد توجه، فعالیت‌ها و دستاوردهای خود بسازد و مدیریت کند.
دانشجو می‌تواند مهارت‌ها را به چند حوزه متصل کند، سطح خوداظهاری و وضعیت
یادگیری را ثبت کند و چیدمان نقشه را شخصی‌سازی کند.

**اصل کلیدی:** گراف لایه نمایش و سازمان‌دهی اطلاعات است، نه منبع اصلی
داده. اطلاعات رسمی باید از سامانه‌ها و جداول مرجع دانشگاه خوانده شوند و
داده‌های شخصی فقط در جداول اختصاصی این ماژول نگهداری شوند.

### اهداف

- نمایش تصویری مهارت‌ها و علایق دانشجو.
- کمک به سازمان‌دهی مسیر یادگیری و توانمندی‌ها.
- اتصال یک مهارت به چند حوزه.
- تعیین سطح نمایش و حریم خصوصی.
- استفاده مجدد از اطلاعات رسمی سامانه دانشگاه.
- ایجاد زیرساخت توسعه قابلیت‌های آتی مانند پیشنهاد مسیر یادگیری.

### اصطلاحات

| اصطلاح      | تعریف                                   |
|-------------|-----------------------------------------|
| Graph       | مجموعه Nodeها و Edgeهای مرتبط           |
| Node        | عنصر گراف مانند دانشجو، مهارت یا حوزه   |
| Edge        | رابطه میان دو Node                      |
| Domain      | حوزه موضوعی مانند برنامه‌نویسی یا هنر    |
| Skill       | مهارت مشخص مانند Python                 |
| Interest    | موضوع مورد علاقه دانشجو                 |
| Achievement | دستاورد یا فعالیت                       |
| Layout      | موقعیت و چیدمان بصری Nodeها             |
| Catalog     | فهرست مرجع که مدیر سامانه نگهداری می‌کند |

## ۲. دامنه

### داخل محدوده

- ایجاد و مدیریت نقشه شخصی دانشجو.
- افزودن و حذف حوزه‌ها از نقشه.
- ثبت مهارت شخصی و اتصال آن به چند حوزه.
- ثبت سطح مهارت و وضعیت یادگیری.
- ثبت علایق و دستاوردهای شخصی.
- نمایش داده‌های رسمی قابل دریافت از سامانه‌های مرجع.
- جابه‌جایی Nodeها و ذخیره Layout.
- تنظیم سطح نمایش و حریم خصوصی.
- مدیریت کاتالوگ حوزه‌ها و مهارت‌های استاندارد توسط مدیر مجاز.
- ثبت عملیات مدیریتی در Audit Log.

### خارج از محدوده نسخه اول

- ارزیابی رسمی و قطعی سطح مهارت.
- صدور گواهی مهارت.
- شبکه اجتماعی و پیام‌رسانی کامل.
- رتبه‌بندی عمومی دانشجویان.
- پیشنهاد قطعی مسیر شغلی یا تحصیلی.
- انتشار عمومی اینترنتی، مگر با تصویب سیاست دانشگاه.

## ۴. اصول طراحی

1.  گراف منبع اصلی داده نیست.
2.  داده‌های رسمی از سامانه‌های مرجع خوانده می‌شوند.
3.  داده‌های شخصی دانشجو مالک مشخص دارند.
4.  کاتالوگ سیستمی از محتوای شخصی جداست.
5.  Graph Engine مشترک و منطق دامنه مستقل است.
6.  حریم خصوصی در نسخه اول به‌صورت پیش‌فرض خصوصی است.
7.  تغییر Layout نباید داده معنایی را تغییر دهد.
8.  تمام عملیات حساس در Backend اعتبارسنجی می‌شوند.

## ۵. رابط کاربری و تجربه گرافی

صفحه اصلی شامل Canvas بی‌نهایت با Dot Pattern، Node مرکزی دانشجو، Nodeهای
حوزه و مهارت و علاقه، Edgeها، Toolbar، پنل جزئیات، Popup و Mini-map است.

رفتارهای موردنیاز: - Pan با Drag فضای خالی Canvas. - Zoom با Scroll یا
کنترل‌های ابزار. - انتخاب Node و مشاهده جزئیات. - جابه‌جایی Nodeهای شخصی
مجاز. - افزودن و حذف حوزه، مهارت و علاقه. - ذخیره و بازیابی موقعیت
Nodeها. - نمایش وضعیت‌های Loading، Empty، Error، Read-only و Normal. -
پشتیبانی از نمایشگرهای کوچک و راست‌به‌چپ.

Node مرکزی دانشجو می‌تواند نام نمایشی و تصویر پروفایل مجاز را نشان دهد.
اطلاعات حساس نباید در گراف نمایش داده شوند. رنگ نباید تنها راه تشخیص نوع
Node باشد؛ آیکون، شکل یا برچسب نیز استفاده شود.

## ۶. مدل مفهومی گراف

### انواع Node

| نوع           | توضیح             | منبع                    |
|---------------|-------------------|-------------------------|
| `student`     | صاحب نقشه         | سامانه دانشجویان        |
| `domain`      | حوزه موضوعی       | کاتالوگ + انتخاب دانشجو |
| `skill`       | مهارت دانشجو      | داده شخصی یا کاتالوگ    |
| `interest`    | علاقه دانشجو      | داده شخصی               |
| `achievement` | دستاورد           | شخصی یا رسمی            |
| `course`      | درس مرتبط         | سامانه آموزشی           |
| `event`       | رویداد یا جشنواره | سامانه فرهنگی           |
| `certificate` | گواهی             | سامانه صادرکننده        |

نسخه حداقلی باید شامل `student`، `domain`، `skill` و `interest` باشد.
انواع رسمی پس از شناسایی منابع داده فعال می‌شوند.

### انواع Edge

| نوع               | مبدأ                  | مقصد                  | توضیح                  |
|-------------------|-----------------------|-----------------------|------------------------|
| `has_domain`      | student               | domain                | حوزه انتخاب‌شده         |
| `has_interest`    | student               | interest/domain       | علاقه ثبت‌شده           |
| `has_skill`       | student               | skill                 | مهارت دانشجو           |
| `belongs_to`      | skill                 | domain                | تعلق مهارت به حوزه     |
| `related_to`      | skill/domain/interest | skill/domain/interest | ارتباط موضوعی          |
| `has_achievement` | student               | achievement           | دستاورد دانشجو         |
| `demonstrates`    | achievement           | skill                 | دستاورد مرتبط با مهارت |
| `based_on`        | skill                 | course                | ارتباط با درس          |
| `participated_in` | student               | event                 | شرکت در رویداد         |

Backend باید ترکیب نوع مبدأ و مقصد را اعتبارسنجی کند. یک مهارت می‌تواند
به چند حوزه متصل شود.

## ۷. سطح مهارت و وضعیت یادگیری

سطح مهارت خوداظهاری است و نباید ارزیابی رسمی تلقی شود.

مقادیر سطح: - `beginner` - `elementary` - `intermediate` - `advanced` -
`expert`

وضعیت یادگیری مستقل از سطح است: - `interested`: علاقه‌مند به یادگیری -
`learning`: در حال یادگیری - `practiced`: تمرین یا استفاده عملی -
`proficient`: تسلط از دید دانشجو - `archived`: بایگانی‌شده

فیلدهای تکمیلی مهارت می‌تواند شامل عنوان، توضیح، سطح، وضعیت، تاریخ شروع،
آخرین به‌روزرسانی و منبع باشد. فیلدهای غیرضروری اجباری نشوند.

## ۸. حوزه‌ها و علایق

حوزه‌های پایه توسط مدیر مجاز تعریف می‌شوند. هر حوزه می‌تواند عنوان، توضیح،
آیکون، وضعیت فعال/غیرفعال و حوزه والد داشته باشد. نمونه‌ها: توسعه
نرم‌افزار، شبکه و امنیت، اینترنت اشیا، هوش مصنوعی، طراحی و هنر و
کارآفرینی.

دانشجو با افزودن حوزه، رکورد کپی‌شده از کاتالوگ نمی‌سازد؛ بلکه یک ارتباط
میان دانشجو و حوزه مرجع ایجاد می‌شود.

حوزه سفارشی دانشجو در صورت فعال شدن باید مالک مشخص، عنوان اعتبارسنجی‌شده
و سیاست نمایش و حذف داشته باشد. تبدیل حوزه سفارشی به کاتالوگ عمومی فقط
با فرایند مدیریتی مجاز است.

اگر علاقه ویژگی مستقل و چرخه عمر جداگانه ندارد، می‌توان آن را به‌صورت
انتخاب حوزه یا رابطه نگهداری کرد. جدول مستقل علاقه فقط زمانی لازم است که
نیازهای داده‌ای مستقل وجود داشته باشد.

## ۹. دستاوردها و داده رسمی

دستاورد شخصی باید با برچسب «ثبت‌شده توسط دانشجو» مشخص شود و بدون بررسی،
تأییدشده تلقی نشود.

گواهی، شرکت در جشنواره، رتبه یا گذراندن دوره باید از سامانه مرجع خوانده
شود. منبع، شناسه رکورد مرجع و وضعیت تأیید باید حفظ شوند. از تکثیر بی‌دلیل
داده رسمی در جداول شخصی خودداری شود.

## ۱۰. Layout و چیدمان

- Layout اولیه می‌تواند شعاعی یا خوشه‌ای باشد.
- دانشجو در مرکز قرار می‌گیرد.
- حوزه‌ها در خوشه‌های نزدیک به مرکز و مهارت‌ها پیرامون حوزه‌های مرتبط قرار
  می‌گیرند.
- موقعیت Nodeها در مختصات فضای گراف ذخیره شود، نه مختصات پیکسلی صفحه.
- پس از جابه‌جایی کاربر، موقعیت‌ها در مراجعات بعدی حفظ شوند.
- افزودن Node جدید نباید کل Layout قبلی را بی‌دلیل جابه‌جا کند.
- Layout باید نسخه‌بندی شود.
- در نبود Layout، چیدمان اولیه deterministic تولید شود؛ ورودی یکسان،
  خروجی یکسان.

## ۱۱. حریم خصوصی و سطح نمایش

سطوح پیشنهادی: - `private`: فقط خود دانشجو و نقش‌های مجاز طبق سیاست
دانشگاه. - `university`: کاربران مجاز داخل دانشگاه. - `selected_roles`:
نقش‌ها یا گروه‌های انتخاب‌شده. - `public`: نمایش عمومی، فقط در صورت تصویب
سیاست دانشگاه.

پیش‌فرض نسخه اول `private` است. عمومی بودن نقشه به معنی عمومی بودن تمام
جزئیات Nodeها نیست. اطلاعات حساس مانند شماره ملی، شماره تماس شخصی،
اطلاعات مالی و نشانی نباید در گراف نمایش داده شوند. API باید داده
غیرمجاز را اصلاً برنگرداند.

## ۱۳. نیازمندی‌های غیرعملکردی

### کارایی و مقیاس‌پذیری

- دریافت گراف در شرایط عادی باید سریع باشد.
- از واکشی غیرضروری داده‌های بزرگ جلوگیری شود.
- کاتالوگ‌ها در صورت نیاز Cache شوند.
- ذخیره Layout به‌صورت کنترل‌شده انجام شود تا درخواست‌های پرتعداد تولید
  نشود.
- در گراف‌های بزرگ از فیلتر، خوشه‌بندی یا بارگذاری تدریجی استفاده شود.

### امنیت

- همه Endpointها احراز هویت و مجوزسنجی شوند.
- مالکیت Node و Edge در Backend بررسی شود.
- ورودی‌ها اعتبارسنجی و در برابر SQL Injection و XSS محافظت شوند.
- داده حساس در Log عمومی ثبت نشود.
- HTTPS، محدودسازی نرخ درخواست و مدیریت امن خطا رعایت شود.

### دسترس‌پذیری و نگهداری

- رابط در اندازه‌های مختلف صفحه قابل استفاده باشد.
- کنترل‌های اصلی با صفحه‌کلید نیز قابل دسترسی باشند.
- کنتراست و تم روشن/تاریک رعایت شود.
- منطق دامنه در کامپوننت‌های گرافی پراکنده نشود.
- API و Layout قابلیت توسعه و سازگاری عقب‌رو داشته باشند.

## ۱۴. معماری پیشنهادی

معماری سه لایه دارد:

1.  **Frontend Graph UI:** Canvas، Node، Edge، پنل جزئیات و تعاملات.
2.  **Graph Application/API:** دریافت داده، اعتبارسنجی، کنترل مالکیت و
    ساخت DTO گراف.
3.  **University Data Sources:** دیتابیس و سرویس‌های فعلی دانشگاه.

پیشنهاد Frontend: - React و TypeScript - React Flow / XYFlow - Zustand -
TanStack Query - Tailwind CSS - Radix UI - Dagre یا ELK برای Layout
اولیه

این فناوری‌ها پیشنهادند، نه الزام. Backend باید با فناوری و استانداردهای
فعلی دانشگاه یکپارچه شود؛ ساخت Backend مستقل فقط برای گراف توصیه نمی‌شود.

Graph Engine مشترک مسئول Pan، Zoom، Drag، انتخاب Node، نمایش Edge و
Mini-map است. منطق مهارت، علاقه، مالکیت و مجوزها در لایه اختصاصی همین
ماژول باقی می‌ماند.

## ۱۵. مدل داده پیشنهادی

نام جدول‌ها پیشنهادی است و باید با استاندارد دیتابیس دانشگاه تطبیق داده
شود. پیشوند `ug_` برای University Graph در نظر گرفته شده است.

### `ug_domains`

کاتالوگ حوزه‌ها: - `id` - `parent_id` - `title` - `slug` -
`description` - `icon` - `is_active` - `sort_order` - `created_at` -
`updated_at`

### `ug_student_domains`

حوزه‌های انتخاب‌شده دانشجو: - `id` - `student_id` - `domain_id` -
`custom_title` (اختیاری) - `description` - `visibility` - `created_at` -
`updated_at`

روی ترکیب `student_id` و `domain_id` باید محدودیت یکتا اعمال شود.

### `ug_skills`

مهارت‌های شخصی: - `id` - `student_id` - `title` - `description` -
`level` - `learning_status` - `source_type` - `catalog_skill_id`
(اختیاری) - `visibility` - `started_at` - `created_at` - `updated_at` -
`archived_at`

### `ug_skill_domains`

جدول واسط چندبه‌چند: - `id` - `skill_id` - `student_domain_id` -
`created_at`

ترکیب مهارت و حوزه باید یکتا باشد و Backend بررسی کند هر دو متعلق به یک
دانشجو باشند.

### `ug_achievements`

دستاورد شخصی یا ارجاع به دستاورد رسمی: - `id` - `student_id` - `title` -
`description` - `achievement_type` - `source_type` - `source_system` -
`source_record_id` - `verification_status` - `achieved_at` -
`visibility` - `created_at` - `updated_at`

### `ug_graph_edges`

در صورت نیاز به روابط عمومی: - `id` - `student_id` - `source_type` -
`source_id` - `target_type` - `target_id` - `edge_type` - `metadata`
(JSON) - `created_at` - `updated_at`

**ملاحظه:** مدل polymorphic انعطاف‌پذیر است اما Foreign Key واقعی به چند
جدول را دشوار می‌کند. Backend باید وجود Nodeها، مالکیت و مجاز بودن نوع
رابطه را بررسی کند. برای روابط مهم از جدول واسط اختصاصی استفاده شود.

### `ug_graph_layouts`

- `id`
- `student_id`
- `graph_type`
- `layout_version`
- `layout_data` (JSON)
- `updated_at`

برای هر دانشجو و نوع گراف یک Layout فعال نگهداری شود.

### `ug_audit_logs`

- `id`
- `actor_id`
- `action`
- `entity_type`
- `entity_id`
- `before_data`
- `after_data`
- `created_at`

از ثبت داده حساس غیرضروری در Audit Log خودداری شود.

### جداول اختیاری

- `ug_skill_catalog`: در صورت نیاز به کاتالوگ مهارت استاندارد.
- `ug_interests`: فقط در صورت نیاز به چرخه عمر مستقل علاقه.
- `ug_node_preferences`: برای تنظیمات نمایشی مستقل از Layout.

## ۱۶. یکپارچگی داده

- هر رکورد شخصی باید مالک معتبر داشته باشد.
- مهارت فقط به حوزه‌ای متصل شود که در نقشه همان دانشجو وجود دارد، مگر
  سیاست دیگری تصویب شود.
- دانشجو نباید بتواند داده دانشجوی دیگر را تغییر دهد.
- حذف حوزه دارای وابستگی باید سیاست روشن داشته باشد: حذف اتصال، جلوگیری
  از حذف یا غیرفعال‌سازی.
- غیرفعال‌سازی حوزه کاتالوگ نباید داده تاریخی را حذف کند.
- عملیات چندمرحله‌ای در Transaction اجرا شوند.
- شناسه رکورد مرجع همراه نوع سامانه نگهداری شود.

## ۱۷. APIهای پیشنهادی

مسیرها نمونه‌اند و باید با الگوی API دانشگاه هماهنگ شوند.

| متد    | مسیر                                             | کاربرد                |
|--------|--------------------------------------------------|-----------------------|
| GET    | `/api/graph/skills/me`                           | دریافت گراف شخصی      |
| GET    | `/api/skills/domains`                            | دریافت کاتالوگ حوزه‌ها |
| POST   | `/api/graph/skills/me/domains`                   | افزودن حوزه           |
| DELETE | `/api/graph/skills/me/domains/{studentDomainId}` | حذف حوزه از نقشه      |
| POST   | `/api/graph/skills/me/skills`                    | ایجاد مهارت           |
| PATCH  | `/api/graph/skills/me/skills/{skillId}`          | ویرایش مهارت          |
| DELETE | `/api/graph/skills/me/skills/{skillId}`          | حذف/بایگانی مهارت     |
| POST   | `/api/graph/skills/me/edges`                     | ایجاد رابطه           |
| PUT    | `/api/graph/skills/me/layout`                    | ذخیره Layout          |
| GET    | `/api/graph/skills/nodes/{nodeType}/{nodeId}`    | جزئیات Node           |
| POST   | `/api/admin/skills/domains`                      | ایجاد حوزه توسط مدیر  |
| PATCH  | `/api/admin/skills/domains/{domainId}`           | ویرایش حوزه           |
| DELETE | `/api/admin/skills/domains/{domainId}`           | غیرفعال‌سازی/حذف حوزه  |

### نمونه ایجاد مهارت

``` json
{
  "title": "TypeScript",
  "description": "برنامه‌نویسی با TypeScript",
  "level": "intermediate",
  "learningStatus": "learning",
  "domainIds": ["student-domain-id"]
}
```

### نمونه ذخیره Layout

``` json
{
  "layoutVersion": 1,
  "nodes": [
    {
      "nodeType": "skill",
      "nodeId": "skill-id",
      "x": 420,
      "y": 180
    }
  ]
}
```

شناسه دانشجو باید از هویت احراز‌شده استخراج شود، نه از پارامتر قابل
دست‌کاری کلاینت. در ذخیره Layout نیز فقط Nodeهای متعلق به گراف همان
دانشجو پذیرفته شوند.

### خطاهای استاندارد

- `400`: ورودی نامعتبر
- `401`: احراز هویت نشده
- `403`: مجوز ناکافی
- `404`: موجودیت پیدا نشد یا قابل مشاهده نیست
- `409`: تعارض یا رابطه تکراری
- `422`: نقض قواعد دامنه
- `500`: خطای غیرمنتظره

پیام خطا نباید وجود داده متعلق به کاربران دیگر را افشا کند.

## ۱۸. اعتبارسنجی و قواعد کسب‌وکار

- عنوان مهارت و حوزه خالی نباشد.
- طول عنوان و توضیح محدود شود.
- `level` و `learning_status` فقط مقادیر مجاز بپذیرند.
- رابطه تکراری جلوگیری یا به‌صورت idempotent مدیریت شود.
- نوع Edge با نوع Nodeهای دو طرف سازگار باشد.
- مالکیت شناسه‌های ارسالی بررسی شود.
- تغییر سطح نمایش مطابق سیاست دانشگاه باشد.
- حذف Node تکلیف Edgeهای وابسته را روشن کند.

## ۱۹. احراز هویت و امنیت

از Authentication فعلی دانشگاه استفاده شود. شناسه کاربر و شناسه دانشجو
از Claims یا نشست معتبر استخراج شوند.

دانشجو فقط داده خود را مدیریت می‌کند. مشاهده نقشه دیگران تنها با سیاست و
مجوز روشن مجاز است. Endpoint جزئیات Node نیز باید مجوز را مستقل بررسی
کند.

برای جلوگیری از IDOR، تمام شناسه‌های Node، Edge و دانشجو از نظر مالکیت
بررسی شوند. غیرقابل حدس بودن UUID به‌تنهایی کنترل امنیتی کافی نیست.

## ۲۰. اتصال به سامانه‌های مرجع

منابع احتمالی: - سامانه اطلاعات دانشجویان. - سامانه آموزشی برای دروس و
سوابق مجاز. - سامانه فرهنگی و رویدادها. - سامانه گواهی‌ها. - سامانه‌های
مهارتی یا کارآموزی.

برای هر منبع باید مالک داده، روش دسترسی، شناسه یکتا، تناوب همگام‌سازی،
رفتار هنگام قطعی، سیاست اصلاح/حذف و سطح مجاز نمایش مشخص شود.

نسخه اول می‌تواند با حداقل منابع لازم عرضه شود. داده رسمی بدون دلیل در
جداول شخصی کپی نشود.

## ۲۱. گزارش‌گیری و ممیزی

رویدادهای قابل ثبت: - ایجاد، ویرایش و غیرفعال‌سازی حوزه کاتالوگ. - تغییر
تنظیمات عمومی. - عملیات مدیریتی روی داده کاربران. - تغییرات حساس سطح
نمایش، در صورت نیاز. - خطاهای امنیتی مهم.

Log باید انجام‌دهنده، زمان، نوع عملیات و موجودیت هدف را ثبت کند. مدت
نگهداری مطابق سیاست دانشگاه تعیین شود.

## ۲۲. آزمون و معیار پذیرش

### آزمون عملکردی

- دانشجو فقط گراف خود را دریافت کند.
- افزودن و حذف حوزه کار کند.
- ایجاد، ویرایش و بایگانی مهارت کار کند.
- اتصال چندگانه مهارت به حوزه پشتیبانی شود.
- سطح مهارت و وضعیت یادگیری مستقل ذخیره شوند.
- Layout پس از بارگذاری مجدد حفظ شود.
- افزودن Node باعث جابه‌جایی غیرضروری Nodeهای قبلی نشود.
- کاربر غیرمجاز نتواند جزئیات Node خصوصی را دریافت کند.
- مدیر مجاز کاتالوگ را مدیریت کند.
- غیرفعال‌سازی حوزه داده‌های قبلی را ناخواسته حذف نکند.

### آزمون امنیتی

- دست‌کاری شناسه دانشجو.
- دست‌کاری شناسه مهارت، حوزه و Edge.
- ایجاد Edge با نوع نامعتبر.
- ارسال سطح یا وضعیت خارج از مقادیر مجاز.
- مشاهده داده خصوصی از Endpoint جزئیات.
- بررسی ثبت عملیات مدیریتی.

### معیار پذیرش MVP

1.  نمایش نقشه شخصی دانشجو.
2.  افزودن و حذف حوزه.
3.  ایجاد، ویرایش و بایگانی مهارت.
4.  اتصال مهارت به چند حوزه.
5.  ثبت سطح و وضعیت یادگیری.
6.  ذخیره موقعیت Nodeها.
7.  کنترل مالکیت در Backend.
8.  خصوصی بودن پیش‌فرض.
9.  قابلیت استفاده در اندازه‌های رایج صفحه.

## ۲۶. پیشنهاد محدوده نسخه اول (MVP)

نسخه اول شامل: - Node مرکزی دانشجو. - کاتالوگ حوزه‌های استاندارد. -
افزودن و حذف حوزه. - ایجاد، ویرایش و بایگانی مهارت. - ثبت سطح خوداظهاری
و وضعیت یادگیری. - اتصال چندگانه مهارت به حوزه. - ثبت ساده علاقه. -
Canvas با Pan، Zoom، Drag و Mini-map. - Layout اولیه خوشه‌ای/شعاعی و
ذخیره چیدمان. - حریم خصوصی خصوصی به‌صورت پیش‌فرض. - کنترل مالکیت و مجوز در
Backend. - پنل پایه مدیریت کاتالوگ.

اتصال به دستاوردهای رسمی، دوره‌ها، رویدادها، گواهی‌ها، انتشار برای دیگران
و پیشنهاد هوشمند مسیر یادگیری به فازهای بعد منتقل شوند.

## ۲۷. جمع‌بندی

ماژول Student Skills & Interests Graph باید نقشه‌ای شخصی، تعاملی و قابل
توسعه برای نمایش مهارت‌ها و علایق دانشجو باشد. طراحی باید میان داده‌های
مرجع دانشگاه و داده‌های شخصی تمایز روشن ایجاد کند. گراف لایه نمایش است و
قواعد مالکیت، اعتبارسنجی و دسترسی باید در Backend اجرا شوند.

پیشنهاد می‌شود Graph Engine برای کل University Graph مشترک باشد، اما مدل
دامنه، APIها، سیاست‌های امنیتی و داده‌های شخصی این ماژول مستقل باقی
بمانند. این تفکیک توسعه ماژول‌های بعدی را ساده‌تر و کم‌هزینه‌تر می‌کند.
